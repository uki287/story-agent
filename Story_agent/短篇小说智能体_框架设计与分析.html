智能体开发实战 · 教学讲义（框架与分析篇）

短篇小说生成智能体
—— 从流程图到可落地框架

学习者可通过输入「主题 + 要求」，让智能体自动产出一篇短篇小说。本讲义不写实现代码，专注于流程诊断与框架设计，为后续编码阶段立下蓝图。

教学对象：具备 Python 基础、了解大模型 API 调用的同学  ·  参考工程：E:\react-agent（手写 ReAct Agent 教学项目）

0导读：这节课要解决什么

先明确我们手里的"题面"，再决定怎么搭框架。

学习目标

  1. 会读图：能逐节点说清一张智能体流程图里每个框、每条箭头的职责。
  2. 会挑错：能识别流程图中的逻辑断点，并判断其严重程度。
  3. 会设计：能为一类"多步骤创作任务"设计出分层的智能体框架。
  4. 会权衡：理解为什么要有记忆层、为什么必须有循环终止条件。

为什么要先做框架，再写代码

很多同学拿到题目第一反应是"赶紧写代码"。但智能体开发和普通函数开发不同：它的复杂度不在语法，而在控制流与状态管理——谁在什么时候调用谁、结果存哪里、什么时候停。这些想不清楚，代码写得越快，返工越狠。

一句话原则 流程图是"需求的骨架"，框架是"骨架的分层实现"。先让骨架正确，再往上填肉。

本讲义范围

本文只做到"框架与分析"这一步：定义清楚有哪些层、每层职责、层与层之间的数据契约，并给出实现计划。真正的编码与运行，留到下一阶段。

1读懂原流程图：逐节点解剖

先看懂，再评判。这是分析任何系统的通用第一步。

1.1 节点逐一拆解

节点它是什么在本系统里的职责
用户输入主题流程起点接收用户的一句话主题，如"一只想飞的猫"。
Agent 核心循环系统的"大脑"反复决策"下一步做什么"，直到可以收尾。这是智能体区别于普通流水线的地方。
Skill 选择（菱形）路由器根据当前状态，决定调用哪一个技能。
OutlineSkill技能：结构生成故事大纲／分节骨架。
大纲审批门 ★新增人在环 · 早期检查点先由 OutlineSkill 产出精简摘要卡（约 150 字）供用户快速验收；通过后再展开为详细大纲。用户可就地修改或换方向重生成。
SearchSkill技能：素材检索背景知识、细节素材。
CharacterSkill技能：人物设计角色卡片（性格、动机、外貌）。
StyleSkill技能：文体确定语言风格（人称、句式、节奏）。
EvalSkill技能：质检对成稿打分并列出问题。
HITL 审批门（终稿）人在环 · 后期检查点把成稿交给人类审阅：满意则批准，不满意则提修改意见。
输出最终作品流程终点交付成稿。

注：原图写作 HTL，业界通用缩写为 HITL（Human-in-the-Loop，人类在环）。这是一处笔误，本文统一修正为 HITL。

1.2 什么是"Agent 核心循环"

这是全图最关键、也最容易被画错的概念。智能体之所以"智能"，是因为它在一个循环里不断做四件事：

Thought（思考） → Action（选一个技能并调用） ↑ ↓ └──── Observation（观察技能返回的结果）

这个"思考—行动—观察"的闭环，就是 ReAct（Reasoning + Acting）范式的核心。它意味着：技能执行完，结果必须回到循环里，模型才能据此决定下一步。

这就是原图最大的问题 原图中所有技能都是"死胡同"——没有任何箭头指回核心循环。这样一来，"循环"名存实亡，系统退化成一条单向流水线，失去了根据中间结果动态调整的能力。

2流程会诊：12 处必须修改的地方

按严重程度分级：致命（不修就跑不通）／高／中／低。

#问题级别修改方案与理由
1 技能结果无回填箭头，ReAct 循环断裂 致命 为每个技能补一条 Observation → 核心循环 的回边。理由：不回填，模型就不知道技能干了什么，无法决策下一步。
2 缺少正文撰写技能 DraftSkill 致命 新增草稿技能，置于评估之前。理由：评估的对象必须是"已写好的正文"；没有它，EvalSkill 会空转。
3 缺少记忆模块，跨步骤信息不共享 致命 引入共享工作台 StoryContext。理由：大纲、人物、风格要被"正文技能"复用，否则长文前后矛盾。
4 只接收"主题"，没有"要求"输入 高 输入改为 主题 + 要求 二元组。理由：字数、风格、受众、禁忌都是硬约束，缺了只能靠猜。
5 缺需求解析环节，自然语言直接进循环 高 新增"解析层"，把自然语言转成结构化 StorySpec。理由：给整条流水线一份统一的"需求合同"。
6 无最大步数 / 预算 / 超时控制 高 设 max_steps 硬上限 + token 预算熔断。理由：防止"评估→重写→再评估"无限循环，烧光费用。
7 "Skill 选择"画成菱形但并非真值判定 中 改为"技能路由器（Router / Dispatcher）"。理由：菱形在标准流程图里表示二值判定，这里是多分支选择，语义不同。
8 评估不合格后没有修订分支 中 补 分数 < 阈值 → 修订 → 回循环。理由：质检的意义在于触发改进，否则评估只是打印一个分数。
9 HITL 的"修改意见"如何进入循环未说明 中 把人工反馈作为带上下文的输入重新进入循环。理由：否则"修改"箭头指向哪里语义不明，模型也收不到反馈内容。
10 批准后缺"组装成稿"步骤 中 新增"产出层"：拼装标题 + 正文 + 元数据。理由：草稿不等于成稿，交付物需要统一格式化。
11 命名 HTL 实为 HITL 低 统一改用 HITL（Human-in-the-Loop）。理由：术语一致性，避免读者误解。
12 无重试与错误兜底 低 技能异常捕获，把错误文本回填给模型自纠。理由：参数幻觉、解析失败是常态，系统不能一遇错就崩。
教学重点：为什么说 1、2、3 是"致命"而非"待优化"？ 拿盖房子打比方：问题 1 是承重墙没砌上（循环结构不成立）；问题 2 是厨房压根没设计（核心功能缺失）；问题 3 是没打地基（状态无处安放）。这三条不解决，后面的门窗装饰（低优先级问题）毫无意义。

3框架设计：六层架构

把"修补后的流程图"重新组织成分层结构——这是从"图"到"工程"的关键一步。

3.1 为什么用"分层"来组织

一张流程图能表达"顺序"，但表达不了"职责边界"。分层的好处是：每层只对上一层负责，变化被隔离在层内。比如以后把 mock 检索换成真实搜索 API，只动技能层，其余层不受影响。这正是软件工程里的"关注点分离"。

① 交互层
Interaction —— 与人对话的全部出入口。接收 主题 + 要求；把解析结果回显给用户确认；并承担两道审核门（大纲审批门、终稿审批门）的问答；同时实时回显智能体的思考与技能调用过程，避免用户长时间面对空白屏幕。
关键点：这一层只做"收发"，不含任何业务逻辑。
② 解析层新增
Requirement Parser —— 把模糊的自然语言，翻译成结构化规格 StorySpec（题材、字数、风格、受众、忌宜）。
关键点：它是"需求"的唯一真相来源，下游所有技能都从这里取约束。
③ 编排层
Orchestrator（即原图的"Agent 核心循环"） —— 系统的唯一大脑。负责：跑 ReAct 循环、路由到具体技能、判定是否收敛、执行修订、控制步数与预算，并在两道审核门处暂停、接收人工反馈。
关键点：它自己从不生成内容，只做决策。
④ 技能层
Skill Layer —— 六个"手脚"技能：大纲、素材、人物、风格、正文（新增）、评估。每个技能只做一件小事，输入输出都是清晰的文本。
术语说明：本项目把能力单元统称为技能（Skill），由 SkillRegistry 注册并向模型暴露 schema，Agent 通过技能调用（skill calling）触发，取代传统 Tool / Function Calling 的命名。
⑤ 产出层新增
Assembler —— 把定稿的正文与标题、元数据（字数、风格标签、评估分）拼装成最终交付物。
⑥ 记忆层新增
StoryContext —— 横向支撑层，贯穿编排、能力、产出三层。集中保存：规格、大纲、人物、风格指南、草稿、历次评语。所有技能读写同一份工作台，从而保证长文一致。

3.2 层与层之间的数据契约

分层不等于放任。要让层之间能协作，必须约定"传什么"。下表是本框架的核心契约：

流向传递的数据说明
交互层 → 解析层(topic, requirements) 两段文本用户的原始自然语言。
解析层 → 编排层StorySpec 对象结构化规格，是整个流程的输入基准。
编排层 → 技能层(技能名, 参数JSON)一次只调一个技能，参数由模型给出。
技能层 → 记忆层写入产物（如大纲文本）技能把结果写入 StoryContext。
技能层 → 编排层Observation 文本技能执行结果（或错误信息）回填给循环。
编排层 → 产出层定稿标记当评估达标且人工批准后触发。
产出层 → 交互层最终作品文本交付给用户。
设计检验：怎样判断一个框架"分对了层"？ 做一次"替换实验"——假设把某个技能整个换掉（比如把 SearchSkill 从假检索换成真检索），如果只需要改一个文件、其他层纹丝不动，说明层次划分是成功的。

4六大关键机制

框架定了骨架，这六个机制决定了它"跑起来稳不稳"。

机制一：ReAct 循环（编排层的心脏）

用文本协议驱动最直观，适合教学：每一步让模型输出 Thought 与 Action，我们解析后执行，再把结果作为 Observation 塞回对话历史。如此往复。

messages = [system(技能清单+规则), user(任务)] while 未收敛 and 步数 < 上限: raw = 大模型(messages) # Thought + Action 解析出 (技能名, 参数) 或 "收尾" 若 收尾: 跳出 结果 = 执行技能(技能名, 参数) messages += [assistant(raw), user("Observation: " + 结果)] 收尾 → 质量门 → HITL → 产出

注意两个协议细节（很多同学在这里踩坑）：

  • 技能结果在文本协议下必须以 role="user" 回填，而不是 role="tool"——后者是 OpenAI 原生 Function Calling 专用，强用会报错。
  • 参数必须是合法 JSON。一旦解析失败，不要让程序去猜（比如硬套一个默认参数），而应回传"格式错误，请重试"，让模型自己纠正。

机制二：状态机与终止条件

"循环"必须有出口，否则就是死循环。本框架设三道闸：

闸门触发条件处置
正常收敛模型主动声明收尾，且评估分 ≥ 阈值进入质量门与 HITL。
步数上限步数达到 max_steps强制收尾，用当前最佳草稿交付，并提示"未完全收敛"。
预算熔断累计 token 超过预算立即停止，保护成本。

机制三：记忆与一致性策略

短篇小说的最大风险是"写到后面忘了前面"。记忆层用三招解决：

招数 1 · 集中存放

所有中间产物写进同一个 StoryContext，任何技能都能读到完整上下文。

招数 2 · 显式注入

写正文时，把大纲、人物卡、风格指南一并塞进提示词，模型"照着写"。

招数 3 · 评语回灌

每次评估的问题清单存进记忆，修订时带上，避免改完又犯同样的错。

招数 4 · 关键设定锁定

人物姓名、专有名词一经确定即"冻结"，后续提示词要求不得更改。

机制四：质量门（Eval Gate）

评估技能返回结构化结果，而非一句"写得不错"。建议五个维度各 20 分：主题契合度、结构完整性、人物塑造、语言风格、情感趣味。

{ "score": 82, "维度": { "主题": 18, "结构": 16, "人物": 15, "语言": 17, "情感": 16 }, "问题": ["中段节奏拖沓", "配角动机交代不足"], "建议": ["压缩第三段环境描写", "补一句配角为何出手相助"] }

编排层据此判断：score ≥ 阈值 → 进入 HITL；否则带着"建议"回到循环修订。

机制五：双审核门（人在环 · HITL）

HITL 不是"给用户看一眼"，而是一个可回退的控制点。它有两条完全不同的出口：

  • 批准 → 交给产出层组装成稿。
  • 修改（附意见） → 把用户意见写进记忆，重新进入 ReAct 循环，让模型带着"哪里要改"再跑一轮。
为什么"修改意见"必须结构化地进入循环？ 如果只是弹一句"用户不满意"，模型无从下手。必须把意见变成新的上下文（例如"用户认为结尾太仓促，希望增加一段离别场景"），它才能精准修订。这也解释了原图第 9 条问题为什么必须修。

补充：为什么要在早期再加一道大纲审批门

这是本方案性价比最高的一处改动，理由有三：

  • 改动成本最低：大纲只有几百字，改一句情节成本极低；若等正文成篇再回头改，往往要重写大段文字。
  • 错误放大倍数最小：大纲是骨架，骨架歪了，人物、正文、风格会整体跟着歪，所以要早拦。
  • 用户掌控感更强：让用户在方向层面参与决策，而不是只能对成品说不满意。

两道审核门的定位对比如下：

审核门位置用户可做什么出口
① 大纲审批门 ★新增大纲生成之后、人物与正文之前浏览大纲全貌；就地修改章节与情节走向；或整条退回重写批准则继续；修改则意见入库并重跑大纲
② 终稿审批门质量评估通过之后、交付之前通读成稿；提出细节修改意见批准则组装交付；修改则带意见回循环修订
设计要点：早期门要轻，后期门要重 大纲审批门只审结构与情节走向，交互应当轻快（列表式浏览 + 就地编辑）；终稿审批门审全文质量，允许更细的修改意见。两道门粒度不同，才能既省时间又不漏问题。

补充：大纲审批门的交互形态 —— 先摘要验收，再展开全文

直接把一份详细大纲甩给用户，有两个毛病：篇幅长、看不完；改起来也重。因此这道门采用由粗到细的两段式设计。

阶段产出篇幅作用
第一段 · 摘要卡一句话立意 + 3~5 条主线情节 + 主要人物 + 结局走向约 150 字用户 10 秒内读完，快速判断方向对不对
第二段 · 详细大纲分章 + 每章场景 / 冲突 / 情绪走向数百字仅在摘要通过后才生成，避免在歪骨架上重投入

用户返回内容 → 三种处理

  1. 通过：据此展开详细大纲，写入记忆，继续后续环节。
  2. 就地修改：用户在摘要卡上直接改（如把第三条主线改成雨夜相遇），系统按新内容重生成摘要卡，再确认一轮。
  3. 换方向：用户给出全新方向，回到 OutlineSkill 从头重生成摘要卡。
三条防跑偏规则 ① 用户的每一处修改都记入记忆，作为硬约束，展开详细大纲时必须遵守，防止展开时又跑偏；② 摘要卡验收最多 3 轮，超限自动采用当前版本（这正呼应循环终止条件）；③ 摘要卡必须包含结局走向，否则用户无法判断方向是否可接受。
对实现层的影响（接口约定） OutlineSkill 需支持两种模式：mode=brief 产出摘要卡、mode=detail 产出详细大纲；记忆层相应新增三个键：outline_brief（当前摘要卡）、outline_detail（详细大纲）、outline_locked（用户已确认的硬约束）。

机制六：失败模式防御

智能体最常见的五种"翻车"，以及我们的对策：

失败模式表现对策
无限循环反复"评估→重写"停不下来max_steps 硬上限 + 预算熔断
重复调用用一模一样的参数反复调同一技能记录 (技能名, 参数) 指纹，命中即拦截并提示换招
参数幻觉编造不存在的技能参数捕获异常，把错误文本回填让模型自纠
过早交卷没调过任何技能就"写完了"检测到无技能记录时顶回："请先获取事实依据"
顺序错乱没写正文就去评估前置校验：草稿为空时拒绝执行评估

5一次完整运行的时序

把六层串起来走一遍，理解数据如何流动。

① 用户：「写一篇关于"一只想飞的猫"的童话，1200 字，给 8-12 岁孩子，温暖治愈」 ② 解析层 → StorySpec{ 题材:童话, 字数:1200, 风格:温暖治愈, 受众:儿童 ... } 交互层回显规格，请用户确认 ← 天然的检查点 ③ 编排层启动 ReAct 循环： ├─ Thought: 先搭骨架 → Action: OutlineSkill(mode=brief) → Observation: 摘要卡(约150字) ├─ ★ 大纲审批门（两段式）：先把摘要卡交给用户验收 │ ├─ 用户就地改了一句：第二章改成雨夜相遇 → 作为硬约束入库 → 重生成摘要卡 → 再确认 │ └─ 用户通过摘要卡 → Action: OutlineSkill(mode=detail) → Observation: 详细大纲 → 继续 ├─ Thought: 补细节素材 → Action: SearchSkill → Observation: 猫的习性… ├─ Thought: 定人物 → Action: CharacterSkill → Observation: 主角"阿灰"… ├─ Thought: 定文体 → Action: StyleSkill → Observation: 风格指南… ├─ Thought: 可以动笔了 → Action: DraftSkill → Observation: 正文草稿(写入记忆) └─ Thought: 自查质量 → Action: EvalSkill → Observation: score=71（低于阈值） ④ 编排层判定未达标 → 带着"问题清单"回到循环 → 再调 DraftSkill 修订 → 复查 score=86 ✅ ⑤ 质量门通过 → 终稿审批门：展示成稿与评分 ├─ 用户：批准 → 产出层组装 → 交付 └─ 用户：修改（"结尾太仓促"）→ 意见入库 → 回到 ③ 重跑一轮 ⑥ 产出层输出：标题 + 正文 + 元数据（字数 1180 / 风格 温暖治愈 / 评分 86）

6实现计划（只定接口，不写实现）

框架确定后，下一步是把层拆成模块。这里给出模块清单与职责，作为编码阶段的蓝图。

模块所属层核心职责（接口）
story_llm公共统一大模型客户端：chat() / chat_json()，含 token 统计与 JSON 清洗。
story_spec解析层StorySpec 数据结构 + parse_spec(topic, requirements)。
story_context记忆层StoryContext：读写大纲/人物/风格/草稿/评语。
skills/技能层技能包：一个技能一个文件（outline / search / character / style / draft / eval）+ base.py（技能基类）+ registry.py（SkillRegistry 与技能清单），便于单独阅读与测试。
story_prompt编排层系统提示词模板：注入技能清单、协作协议、循环规则。
story_agent编排层StoryAgent.run(topic, requirements)：ReAct 循环 + 质量门 + HITL。
story_main交互层命令行入口：采集输入、展示进度、处理审批对话。

建议的实现顺序

  1. 先搭骨架：story_llm + story_spec（先让"需求解析"跑通，可独立验证）。
  2. 再补记忆：story_context（很简单，但决定了后面所有技能怎么写）。
  3. 逐个做技能：六个技能各自独立、可单独测试，是天然的可并行单元。
  4. 最后做循环：story_agent 把技能串起来，加质量门与 HITL。
  5. 灰度验证：先用"自动批准"模式跑通全链路，再打开真实 HITL 对话。

验证策略（对应后续 TDD 阶段）

单元级

每个技能单独喂输入，检查输出是否符合 schema（尤其评估技能必须返回合法 JSON）。

契约级

检查解析层输出的 StorySpec 字段是否齐全、字数是否为整数。

集成级

用自动批准模式跑 3 个不同主题，验证能产出完整成稿且不超步数。

鲁棒级

人为制造"参数非法""评估不合格"，确认防御机制生效、不崩溃。

7课堂小结与思考题

核心结论（务必记住这三句）

  1. 没有"回填"就没有循环：技能结果必须回到核心循环，ReAct 才成立。
  2. 没有"记忆"就写不了长文：跨步骤共享上下文，是一致性的前提。
  3. 没有"终止条件"就不是工程：任何循环都必须有出口，否则就是隐患。

思考题

  1. 如果把这套流程从"短篇小说"改成"科研综述"，六个技能里哪几个要换？哪几层不用动？为什么？
  2. 本方案已采纳"两个审批点"：大纲审批门（早）+ 终稿审批门（晚），见机制五。请继续思考：如果再加第三个审批点（如"人物设定确认"），收益递减的临界点在哪里？
  3. 记忆层如果无限增长，会不会撑爆上下文窗口？你会用什么策略做"记忆压缩"？
  4. 如果把评估阈值设得很高（比如 95 分），系统会发生什么？这属于框架问题还是参数问题？

8附录：环境与配置契约

框架要跑起来，必须知道"密钥和地址从哪来"。这部分属于公共层职责，在此明确定义。

8.1 配置文件位置

短篇小说智能体的外部配置独立放在 Story_agent/.env 中，不共用项目根目录的 .env。公共层 story_llm 在导入时读取，其余任何模块都不直接接触密钥。这样整个 Story_agent/ 目录可以单独拷走运行、也能独立更换模型服务商而不影响其他示例。

模板见同目录的 .env.example（不含真实密钥）；两份 .env 都会被 .gitignore 排除。

8.2 变量清单

变量名示例用途
OPENAI_API_KEYsk-********大模型调用的鉴权密钥。本地部署若无需鉴权可留空。
OPENAI_BASE_URLhttps://…/v1OpenAI 兼容端点地址，换服务商时改这里。
MODEL模型名模型名，优先级低于构造参数；代码不提供默认值。

8.3 读取约定（公共层唯一入口）

  • 用 python-dotenv 的 load_dotenv() 在模块导入时加载，但必须显式传入同目录的绝对路径：load_dotenv(Path(__file__).parent / ".env")。若用无参调用，该库会从代码所在目录逐级向上查找，找不到就借用根目录那份，造成两份配置互相干扰且难以排查。
  • 客户端只读取上述变量构造 OpenAI(api_key=..., base_url=...)；不做任何字符串拼接，避免出现非法 URL。
  • 本工程使用 OpenAI 兼容协议，不绑定任何特定服务商，代码里也不写死默认模型名。模型名必须与 BASE_URL 指向的服务商匹配，且必须是账号实际有权限调用的；填错或模型已下线会直接报错，因此三个变量缺失时应在启动阶段立即抛错说明原因。
  • 密钥缺失时，应在启动阶段快速失败并给出清晰提示，而不是拖到第一次调用才报错。
安全提醒（工程规范） .env 内含明文密钥，必须加入 .gitignore，严禁提交到代码仓库；如需分享工程，应提供 .env.example 作为模板（只留变量名，不留真实值）。
